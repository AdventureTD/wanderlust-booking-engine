# Offline reservation semantic reconciliation (candidate)

This disconnected, standard-library Python 3 checker reads owner-supplied exports. It never loads booking runtime modules, uses CMS/network APIs, writes exports, migrates rows, selects physical units, or sends guest/provider output. It prints diagnostic JSON to stdout, not a corrected data file.

```bash
python -B scripts/reconcile-reservation-exports.py --bookings Bookings.json --summaries BookingSummary.csv
python -B -m unittest discover -s tests -p test_reservation_reconciliation_offline.py -v
```

Each file may independently be UTF-8/BOM JSON (a top-level array of objects) or comma-separated CSV with a header. Use exact CMS field IDs: `_id`, `bookingNumber`, `checkIn`, `checkOut`, and for Bookings `roomCode`, `quantity`, `status`. CSV alone explicitly accepts `ID` as `_id`; both headers together are rejected. Other display-name headers are not guessed. Additional fields are ignored for semantic checks and never printed; malformed JSON, nested duplicate keys, duplicate CSV headers and inconsistent CSV widths are rejected. Inputs must be trusted-size local files, not untrusted uploads or streaming datasets.

- Exact nonempty string bookingNumber joins the collections, without trimming, case folding or inventing a booking-number format. System IDs must be nonempty strings and unique within each collection. Multiple distinct room rows with the same bookingNumber are legitimate; multiple Summary rows or conflicting date windows are diagnosed. Duplicate row IDs are reported for every affected row, even if values agree.
- Dates must be valid `YYYY-MM-DD`, with checkout strictly after check-in. Timestamps are **unresolved** (`DATE_INTERPRETATION_REQUIRED`), never converted to a guessed day or timezone. Locale dates and numeric dates are invalid. Exact Bookings/Summary date differences are reported, even when one side is invalid. Preserve original exports; independently establish any canonical date mapping before using a derived diagnostic copy. This stricter offline rule is not the live reader's timestamp interpretation contract.
- Bookings status accepts the pinned inventory vocabulary, case-insensitively with whitespace stripped for classification only: confirmed, hold, blocked, in-house, cancelled, canceled, pending, pending confirmation, checked-out. Summary status is checked only if present; the legacy Summary writer need not emit it. No inactive rows are silently excluded.
- Room classes are exactly adventure_suite, two_bedroom_apartment, penthouse_apartment. Quantity must be a positive integral JSON number (not boolean/string), at most the class capacity (3/1/1 respectively). JSON decimal/exponent tokens are parsed exactly, without binary-float rounding: `1.0`, `1e0` and `30e-1` are accepted, but `1.0000000000000001`, `0.99999999999999999` and `3.0000000000000001` receive `INVALID_QUANTITY`. Nonfinite JSON constants (`NaN`, `Infinity`, `-Infinity`) are invalid exports. CSV quantities still accept canonical unsigned integer text only (not decimal/exponent forms). Quantity 2/3 may be legitimate legacy aggregate occupancy: acceptance here does **not** certify physical-row migration readiness or quantity=1 compliance.
- Blocks without a valid identity or exactly one Summary with a valid positive date window receive `BLOCK_DATE_LINKAGE_MISSING`. A differently dated valid Summary additionally causes `DATE_MISMATCH`; neither date window is selected as correct.

Exit 0 means **no diagnosed issue in these supplied files**, not migration/publication readiness. Exit 1 means diagnostic issues (including empty collection exports); exit 2 means unreadable/invalid export. Output always has `migration_performed: false` and `publication_ready: false`. Issue locations use collection names plus one-based record ordinal, not guest names, emails, booking numbers, system IDs, paths or row values. `row: 0` denotes a collection-level issue. CSV ordinal counts parsed data records, not physical lines in multiline records. Keep the input ordering and original hashed exports to resolve ordinals privately. CLI argument-usage errors are ordinary argparse output; never put guest data into CLI arguments.

## Boundaries and remaining release gates

No claims of actual current reservations reconciled or migrated: all development fixtures are synthetic. This does not certify complete/fresh/coherent exports, authoritative guest identity, physical assignments, claim history, overlaps/capacity across bookings, accepted finances, payment preservation, admin usability, effect suppression, writer drain, or rollback/recovery compatibility. It cannot infer whether same-number same-date rows belong to separate real reservations; owner identity review remains required. No migration actions or allocation recommendations are emitted.

Use this checker separately on each pair of per-collection exports; do not change the comparator or claim one substitutes for the other. That comparator takes a combined JSON object and may print IDs; this checker takes two files and prints no IDs. Neither authorizes a live export, edit or cutover.
