## Privacy / semantics

The logger emits only fixed build/stage strings, primitive own-data descriptor **type labels**, and a fixed `classification` hint on supplied errors: `permission` for exact own primitive code `WDE0027`; `validation` for `WDE0033` or `WDE0076`; otherwise `unclassified`. These meanings come from [Wix Data Error Codes](https://dev.wix.com/docs/velo/apis/wix-data/error-codes): insufficient permissions, nonpositive limit argument, and validation error from a Wix app collection/external database, respectively. This deliberately small allowlist does not classify every Wix error; message-only errors, inherited/accessor codes and unknown codes remain unclassified. No synthetic `PERMISSION_DENIED`/`VALIDATION_ERROR` platform contract is assumed. Tests inject documented-code Error fixtures into the actual backend; they are not captured live failures. No classification changes business decisions. The logger never emits error values, stack traces, request dates, counts, room/booking identifiers or rows. Even error message/code strings can contain personal data, so their values are withheld. Accessors are not read; descriptor/console failures are contained. The old booking-number/count console output is suppressed. This deliberately removes that logging side effect (including failures caused by its JSON serialization/console), not business/query logic. Successful return values are compared structurally; thrown SDK/processing errors preserve original object identity. No cross-invocation correlation is added; concurrent requests can interleave log stages.
